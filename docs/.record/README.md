# .record/ 目录说明

> **定位**: 实施记录归档层 — 记录"实际发生了什么"

---

## 📁 目录结构

```
.record/
├── README.md                    # 本文件：记录规范
├── decisions/                   # 技术决策记录（ADR）
├── issues/                      # 问题修复记录
├── archive/                     # 历史任务归档（从旧 archive/ 迁移）
│   ├── tasks/                   # 按任务编号组织（T3/T4/T5/T6/C07）
│   └── logs/                    # 日志归档
└── reports/                     # 验证报告归档（从旧 reports/ 迁移）
    ├── range/                   # Range 层验证报告
    ├── lifespan/                # Lifespan 层验证报告
    └── validation/              # 修复验证记录
```

---

## 📝 记录类型

### 1. 技术决策记录（ADR - Architecture Decision Record）

**位置**: `decisions/`  
**命名**: `ADR-{编号}-{简短描述}.md`（如 `ADR-001-整数价格设计.md`）

**何时创建**:
- 做了非显而易见的技术选择
- 在多个方案间做了取舍
- 需要记录"为什么这样做"

**模板**:
```markdown
# ADR-{编号}: {标题}

**日期**: 2026-07-XX  
**状态**: 已采纳 / 已弃用 / 已替代  
**决策者**: {谁做的决定}

## 背景

{什么问题需要决策}

## 考虑的方案

### 方案 A: {描述}
**优点**: ...  
**缺点**: ...

### 方案 B: {描述}
**优点**: ...  
**缺点**: ...

## 决策

选择 **方案 X**，因为 {理由}

## 后果

- 正面影响: ...
- 负面影响: ...
- 技术债: ...

## 相关代码

- `src/malf/{module}.py:L123-L456`
- 提交: `abc1234`
```

---

### 2. 问题修复记录

**位置**: `issues/`  
**命名**: `ISSUE-{编号}-{简短描述}.md`（如 `ISSUE-P0-1-Core-Break检测错误.md`）

**何时创建**:
- 发现并修复了 bug
- 规格与实现有矛盾
- 需要记录排查过程

**模板**:
```markdown
# ISSUE-{编号}: {标题}

**发现日期**: 2026-07-XX  
**修复日期**: 2026-07-XX  
**严重程度**: P0 / P1 / P2  
**影响范围**: {哪些模块}

## 问题描述

{什么不对，预期 vs 实际}

## 复现步骤

1. ...
2. ...
3. ...

## 根因分析

{为什么会发生，技术深挖}

## 修复方案

{怎么改的，为什么这样改}

## 验证结果

- [ ] 单元测试通过
- [ ] 真实数据验证通过
- [ ] lineage_hash 确定性检查通过

## 相关代码

- 修改文件: `src/malf/{module}.py`
- 测试文件: `tests/test_{module}.py`
- 提交: `abc1234`

## 经验教训

{下次如何避免}
```

### 3. 历史任务归档

**位置**: `archive/tasks/{任务编号}/`  
**内容**: 从旧 `archive/tasks/` 迁移的历史任务记录

**说明**:
- 保持原有结构不变
- 按任务编号组织（T3, T4, T5, T6, C07）
- 只读参考，不再更新

---

### 4. 验证报告归档

**位置**: `archive/reports/`  
**内容**: 从旧 `reports/` 迁移的验证报告

**说明**:
- 按层级组织（range/, lifespan/, validation/）
- 包含批量测试报告、合规性报告等
- 只读参考，不再更新

## ✍️ 记录原则

### 何时记录

1. **必须记录**:
   - P0/P1 级别问题的修复
   - 重大技术决策（影响架构或算法）
   - 与规格有争议的实现选择

2. **建议记录**:
   - 非显而易见的实现技巧
   - 踩过的坑和解决方案
   - 真实数据验证中的发现

3. **不需记录**:
   - 常规功能实现（代码和测试已说明）
   - 拼写错误、格式调整等琐碎修改
   - 临时调试脚本

### 记录时机

- **即时记录**: 修复问题后立即记录，趁记忆清晰
- **批量归档**: 任务完成后，整理阶段性文档到 `.record/`
- **不要拖延**: 过几天就会忘记细节

## 🔗 与其他层的关系

| 层级 | 目录 | 关系 |
|------|------|------|
| **规格层** | `spec/` | `.record/` 的决策可能反向推动规格补丁 |
| **计划层** | `.plan/` | 实施过程写在 `.plan/`，完成后归档到 `.record/` |
| **记录层** | `.record/` | 本层：只增不改，永久保存 |

**流程**:
```
做决策 → 记录在 .plan/{任务}.md 中
   ↓
实施完成 → 关键决策提取到 .record/decisions/
   ↓
发现问题 → 排查过程记录到 .record/issues/
```

## 📌 命名规范

### 文件命名

- ADR: `ADR-{三位数编号}-{kebab-case-标题}.md`
- Issue: `ISSUE-{优先级}-{编号}-{kebab-case-标题}.md`
- 例子:
  - `ADR-001-integer-price-design.md`
  - `ISSUE-P0-1-core-break-detection-error.md`

### 编号规则

- ADR 编号从 001 递增
- Issue 编号包含优先级前缀（P0/P1/P2）

## 🔍 查找记录

### 按类型查找

```bash
# 查看所有技术决策
ls .record/decisions/

# 查看所有问题修复
ls .record/issues/

# 查看历史任务
ls .record/archive/tasks/
```

### 按关键词搜索

```bash
# 搜索 "break" 相关记录
grep -r "break" .record/ --include="*.md"

# 搜索 P0 级别问题
grep -r "P0" .record/issues/
```
